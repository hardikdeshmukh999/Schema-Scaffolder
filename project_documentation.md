# Enterprise Schema Scaffolder - Documentation

## 1. Project Overview

### Goal & Purpose
The **Enterprise Schema Scaffolder** is an automated pipeline designed to bridge the gap between business requirements and technical database architecture. Its primary purpose is to ingest raw Agile artifacts (Epics and User Stories), use specialized AI agents to extract data models, enforce non-negotiable enterprise standards deterministically, and output a validated, deployment-ready PostgreSQL database schema (DDL).

### Usage & Input/Output
- **Usage**: A user selects a Business Requirements Document (BRD) JSON file from the interface and clicks "Run Scaffolder Pipeline". The system automatically orchestrates a multi-agent workflow to process the requirements.
- **Input**: A JSON file containing structured Agile Epics and User Stories, including dependency mappings (e.g., Story A blocks Story B).
- **Output**: 
  1. A visual Directed Acyclic Graph (DAG) of story execution.
  2. A canonical JSON Intermediate Representation (IRSchema) of the database.
  3. A robust PostgreSQL DDL script, complete with inline compliance comments.
  4. A Static Analysis Linter report verifying syntax and relational integrity.

### Relation to the Solution Accelerator Lifecycle
Based on the provided SDLC accelerator diagram, the Enterprise Schema Scaffolder aggressively accelerates three major pillars:

1. **Discovery**: It natively ingests the outputs of the **"Epics and User Stories"** phase (which may have been generated by the *AI Powered Story Creator*).
2. **Solution Design & Development**: It completely automates the generation of **"Database schema and scripts"**. Rather than a human architect manually reading stories to design tables, the Multi-Agent system handles this translation in seconds.
3. **Governance & Compliance**: It actively enforces **"Follow regulatory requirements"** and **"Ensure audit readiness"** (including SOX/GxP standards). It does this by programmatically injecting standard audit trails (`created_by`, `updated_at`) and using an AI Compliance Officer to apply semantic tagging for HIPAA/PII compliance directly onto the schema before deployment.

## 2. Phase-by-Phase Breakdown

### Phase 1: Validating and Topologically Sorting BRD
- **Brief Description**: Parses the raw JSON input and orders the user stories based on their dependencies using a directed acyclic graph (DAG).
- **What it does exactly**:
  - Validates the JSON against strict Pydantic models (`BRDInput`, `Story`).
  - Extracts explicit dependency maps (e.g., "Blocks S-002").
  - Uses `TopologicalSorter` to arrange stories so foundational entities are processed first.
  - Renders an interactive Mermaid.js diagram in the UI.
- **Purpose**: Ensures that AI agents extract database entities in the correct chronological sequence to build relational hierarchies logically.
- **Input / Output Example**: 
  - *Input (JSON Snippet)*: 
    ```json
    {
      "id": "S-002",
      "dependencies": ["Blocks S-001"]
    }
    ```
  - *Output (Mermaid DAG Snippet)*:
    ```mermaid
    graph LR;
        S002["S-002: Profile Creation"] --> S001["S-001: Login System"]
    ```
- **Advantage**: Prevents AI hallucinations and missing references by supplying context in a structured, hierarchical manner rather than a flat list.
- **Why in this case**: An LLM processing a "Login" story before a "User Registration" story might fail to link the User entity correctly. Topological sorting guarantees structural integrity.

### Phase 2: Generating Canonical IR (Multi-Agent Architecture)
- **Brief Description**: Uses an Anthropic-powered Orchestrator-Worker Multi-Agent system to extract and model database entities from stories.
- **What it does exactly**:
  - Runs **"Extractor"** AI agents in parallel across all sorted stories to identify core domain nouns.
  - Runs a **"Deduplicator"** AI agent to merge overlapping entities (e.g., "Manager" and "Employee" both become "User").
  - Runs a **"Modeler"** AI agent to map the unique entities into a strict Pydantic Intermediate Representation (`IRSchema`).
- **Purpose**: Bridges the gap between natural language business requirements and strict data architecture.
- **Input / Output Example**: 
  - *Input (Topologically Sorted Story JSON)*: 
    ```json
    {
      "id": "S-003",
      "userStory": "As a patient, I want to upload a medical document so my doctor can review it."
    }
    ```
  - *Output (IRSchema JSON Snippet)*:
    ```json
    {
      "name": "medical_document",
      "columns": [
        { "name": "document_url", "data_type": "string" },
        { "name": "patient_id", "data_type": "uuid", "foreign_key_target": "patient.id" }
      ]
    }
    ```
- **Advantage**: Bypasses the token limitations and "lost in the middle" problems of monolithic prompts by dividing the workload into specialized, parallel map-reduce agents.
- **Why in this case**: Enterprise schemas are too complex for a single zero-shot prompt. A multi-agent pattern guarantees higher fidelity and scalability.

### Phase 3: Injecting Enterprise Governance Columns
- **Brief Description**: A deterministic, programmatic pass that enforces internal architectural standards on every table.
- **What it does exactly**:
  - Upgrades or injects standard Primary Keys (ensuring `id` is a UUID).
  - Injects audit tracking columns (`created_at`, `updated_at`, `created_by`).
  - Injects soft-delete flags (`is_deleted`).
- **Purpose**: Enforces enterprise architectural standards without relying on probabilistic AI outputs.
- **Input / Output Example**: 
  - *Input (Raw Table IR)*: Table `medical_document` with only `document_url` and `patient_id`.
  - *Output (Governed Table IR)*: 
    ```json
    {
      "name": "medical_document",
      "columns": [
        { "name": "id", "data_type": "uuid", "is_primary_key": true },
        { "name": "created_at", "data_type": "timestamptz" },
        { "name": "is_deleted", "data_type": "boolean" }
      ]
    }
    ```
- **Advantage**: Guarantees 100% compliance with internal auditing standards (like SOX compliance) across the entire database.
- **Why in this case**: AI models might randomly name primary keys or forget audit trails. Deterministic Python code guarantees these non-negotiable enterprise requirements are never missed.

### Phase 3.5: Semantic Tagging (PII/HIPAA)
- **Brief Description**: An AI-driven compliance officer agent that audits the schema for sensitive data and applies security metadata.
- **What it does exactly**:
  - Analyzes the `IRSchema` using a specialized Anthropic agent.
  - Identifies columns likely to contain PII or PHI based on HIPAA standards (e.g., SSNs, medical records).
  - Populates the `compliance_tags` array for those columns with `@pii_masked` or `@hipaa_classified`.
- **Purpose**: Shifts left on security and compliance, ensuring data privacy standards are embedded into the design phase.
- **Input / Output Example**: 
  - *Input (Governed Column)*: `{ "name": "social_security_number", "data_type": "string" }`
  - *Output (Tagged Column)*: 
    ```json
    { 
      "name": "social_security_number", 
      "data_type": "string", 
      "compliance_tags": ["@pii_masked"] 
    }
    ```
- **Advantage**: Automatically flags risk areas for database administrators before a single line of code goes to production.
- **Why in this case**: Regulatory requirements demand strict data handling. Tagging at the schema level ensures downstream data pipelines or masking policies can automatically identify sensitive columns.

### Phase 5: Compiling SQL AST and Static Analysis Linter
- **Brief Description**: Compiles the IR into raw PostgreSQL DDL and runs strict syntax and integrity checks against the output.
- **What it does exactly**:
  - Uses SQLAlchemy's MetaData registry to compile the `IRSchema` into raw SQL DDL.
  - Uses a Regex engine to inject compliance tags as inline SQL comments (`/* @pii_masked */`).
  - Parses the generated SQL using `sqlglot` to verify perfect PostgreSQL syntax (Check 1).
  - Crawls the schema to ensure all Foreign Key targets exist, preventing ghost tables/columns (Check 2).
  - Verifies indexing strategies (Check 3).
- **Purpose**: Transforms the intermediate format into deployment-ready code and mathematically validates its execution safety.
- **Input / Output Example**: 
  - *Input (IRSchema)*: The fully tagged JSON schema.
  - *Output (PostgreSQL DDL & Linter)*:
    ```sql
    CREATE TABLE medical_document (
        id UUID NOT NULL,
        social_security_number VARCHAR(255) /* @pii_masked */,
        PRIMARY KEY (id)
    );
    ```
    *Linter*: `✅ SQL Syntax: 0 Errors | ✅ Foreign Keys: 100% Valid`
- **Advantage**: Pre-validates the SQL code so developers don't have to discover syntax or relational errors during live database migrations.
- **Why in this case**: AI-generated schemas often hallucinate foreign key relationships. The deterministic linter guarantees the relational integrity of the final product, safely delivering the "Database schema and scripts" for deployment.
